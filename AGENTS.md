# AGENTS.md

Keep it simple. We want clean, readable and functional code. Don't over-engineer and avoid clever tricks where a straightforward approach works. Prefer immutable data and plain methods.

## General Guidelines

- Don't write or change READMEs unless the user specifically asked for it
- Don't add comments or Javadoc in code or build scripts
- Don't run Gradle tasks unless the user asked for it
- Don't touch generated code (`api/build/generated`).

## Code Style

- Stick to the current code style
- Use records for value, request, result and event data instead of classes with getters, setters, `equals` and `hashCode`
- Make classes `final` unless they are meant to be extended, give utility classes a private constructor
- Prefer `private final` fields and constructor injection, no mutable static state
- Prefer early returns and guard clauses over nested ifs
- Use `Optional` for return values that may be absent, not for fields or parameters
- Mark nullable parameters, fields and return values with `org.jetbrains.annotations.Nullable`.
- Async API methods return `CompletableFuture`; don't block on them with `join()` or `get()` in platform or NATS callback code
- Throw specific exceptions with a message, use `CloudApiException` with a `Reason` for API errors, never throw `Exception`, `RuntimeException` or `Throwable`
- Don't swallow exceptions: log them, or name the variable `ignored` or `expected` if ignoring is intended
- One top-level type per file, the file name matches the type

## Logging

- Use `java.util.logging`, one logger per class: `private static final Logger LOGGER = Logger.getLogger(MyClass.class.getName());`
- Plugin entry points may use the logger their platform provides
- Log as little as possible: failures at `SEVERE` or `WARNING`, recoverable things like reconnects, retries and timeouts at `FINE`
- No `System.out`, `System.err` or `printStackTrace()`, pass the exception to the logger instead

## Tests

Write meaningful, clean tests that check the real logic and behavior, not the implementation details. Every test should be able to fail for a real bug. No tests that only restate the code, test getters, setters or mocks, or exist to raise the coverage. Keep them short and readable: shared setup in fields or `@BeforeEach`, one behavior per test.

- JUnit with Mockito; mock third party platform APIs, but test our own logic with real objects where possible
- Assert on outcomes (returned values, sent requests, published messages, state), not on log output
- Test method names are camelCase sentences without underscores, e.g. `rejectedLoginCompletesWithoutASession`
- Tests must run locally without NATS, Docker or a controller; HTTP tests use `ControllerServer`
- Tests that need a real NATS broker are annotated with `@NatsTest` and use `TestNats`
- Use a random network id per NATS test and `Await.until` instead of fixed sleeps

## Checkstyle

The config is `.checkstyle/checkstyle.xml`, every violation fails the build.

- No wildcard imports, except static `Mockito`, `ArgumentMatchers` and `Assertions` and the generated proto packages
- No unused or redundant imports, no unused local variables
- Constants in `UPPER_SNAKE_CASE`, types `PascalCase`, methods, fields, parameters and variables `camelCase`
- Classes with only private constructors must be `final`, utility classes need a private constructor, no constant-only interfaces
- No empty blocks; empty catch blocks are only allowed with a variable named `ignored` or `expected`
- `equals` and `hashCode` together, no `==` on strings, no double brace initialization, no fall-through in `switch`
- Braces are required unless the statement fits on the same line
- `@SuppressWarnings("checkstyle:RuleName")` only if there is really no other way

## Formatting

- Spotless with palantir-java-format, run `./gradlew spotlessApply` before committing
- 4 spaces indent (2 for yaml), UTF-8, final newline
- Keep lines around 120 chars
- Imports in one block, static imports first, as palantir-java-format sorts them

## Commits and Pull Requests

- Don't add Co-Authored-By trailers to commits
- In PR descriptions, mention once at the end that the PR was generated by an agent, as a single plain line with the actual model and tool, e.g. Created with Claude Opus 5.5 in <harness>.
- No emojis, links or badges in that line, e.g. not 🤖 Generated with [Claude Code](https://claude.com/claude-code)
- Use Conventional Commits
